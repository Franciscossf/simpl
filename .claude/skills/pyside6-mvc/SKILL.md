# PySide6 MVC (.py classes)

Skill for creating and maintaining PySide6 applications organized in the **Model-View-Controller** pattern, with the entire interface built in Python code (`.py` classes) — no `.ui` files, no Qt Designer.

## Standard project structure

When creating a new project, ALWAYS use this structure — it is a UI application that runs directly, not a distributable package: `main.py` at the project root and the MVC layers inside `src/`:

```
my_project/
├── main.py                  # Entry point: creates QApplication and the main controller
├── pyproject.toml           # Managed by uv (dependencies and metadata)
├── uv.lock                  # Auto-generated by uv — never edit by hand
├── .python-version          # Python version pinned by uv
├── src/
│   ├── __init__.py
│   ├── models/
│   │   ├── __init__.py
│   │   └── user_model.py        # Data/business logic, NO QtWidgets imports
│   ├── views/
│   │   ├── __init__.py
│   │   ├── main_view.py         # QMainWindow/QWidget built in code
│   │   └── components/          # Reusable widgets (optional)
│   │       └── __init__.py
│   ├── controllers/
│   │   ├── __init__.py
│   │   └── main_controller.py   # Connects View signals to methods, calls the Model
│   ├── workers/                 # QThread workers (optional; see references/threading.md)
│   │   ├── __init__.py
│   │   └── report_worker.py     # One file per worker; for 1–2 workers use utils/workers.py
│   ├── infra/                   # Communication with external systems/devices (optional)
│   │   ├── __init__.py
│   │   └── plc_client.py        # e.g. PLC/serial/socket/HTTP clients, one file per client
│   ├── theme/                   # App styling in code (optional)
│   │   ├── __init__.py
│   │   ├── palette.py           # Color/spacing/font constants
│   │   └── styles.py            # QSS built from the palette + apply_theme(app)
│   ├── utils/
│   │   ├── __init__.py
│   │   ├── constants.py         # Shared constants (app name, sizes, formats)
│   │   ├── validators.py        # Pure validation functions (email, dates, IDs...)
│   │   ├── formatters.py        # Text, currency, date formatting for display
│   │   ├── paths.py             # Path resolution (resources, app data)
│   │   └── config.py            # Reading/writing settings (JSON/ini)
│   └── resources/               # Icons, images, qss (optional)
└── tests/                   # Tests with pytest/pytest-qt (optional)
```

Since `main.py` lives at the root, the project root is added to `sys.path` automatically, and imports use the `src.` prefix in ALL files: `from src.models.user_model import UserModel`, `from src.views.main_view import MainView`. Use this pattern consistently in cross-layer imports too (e.g., the controller imports `from src.models...`). Never use relative imports (`from ..models import ...`).

For small projects (1–2 screens) the same separation applies, but it may live in single files per layer (`model.py`, `view.py`, `controller.py`). Ask the user only if the scope is ambiguous; otherwise choose whatever best fits the size of the request.

## Responsibilities of each layer

**Model** (`models/`)
- Holds data and business rules: validation, calculations, persistence (SQLite, JSON, API...).
- NEVER imports `QtWidgets`. It may inherit from `QObject` and emit `Signal` to notify state changes (observer pattern) — this keeps the Model testable without a UI.
- Expose clear methods (`add()`, `list_all()`, `validate()`) instead of letting the controller poke at internal attributes.

**View** (`views/`)
- Classes inheriting from `QMainWindow`, `QWidget`, or `QDialog`, with all layout assembly in a `_setup_ui()` method called from `__init__`.
- The View is "dumb": it only creates widgets and layouts, and exposes widgets as public attributes (e.g., `self.save_button`, `self.name_field`). It contains no business logic and never accesses the Model directly.
- Display helper methods are allowed and encouraged: `show_error(msg)`, `clear_form()`, `update_table(data)`.

**Controller** (`controllers/`)
- Receives Model and View in the constructor (dependency injection) and wires everything in a `_connect_signals()` method.
- Every click/edit in the View calls a controller method; the controller calls the Model and then tells the View to update.
- Never creates widgets. Never performs business calculations — it delegates to the Model.

**Workers** (`workers/`)
- `QThread` subclasses for long-running operations (see `references/threading.md` for the full standard and templates).
- Generic and self-contained: receive plain data in `__init__`, declare their own signals, do the work in `run()`. Never touch widgets; controllers create them, keep a reference, and connect their signals to View updates.
- Create the folder only when the project has 3+ workers; for 1–2, use a single `src/utils/workers.py` module. Promoting later is just moving each class to its own file and updating imports.

**Infra** (`infra/`)
- Communication with the outside world: hardware and equipment (PLC/CLP, serial, sockets, instruments), HTTP/API clients, message brokers — one client/driver class per file (e.g., `plc_client.py`, `serial_client.py`, `api_client.py`).
- Infra classes know protocols, not the domain: they expose operations like `connect()`, `read(address)`, `write(address, value)`, `request(endpoint)` and return plain data (dict, bytes, dataclass). Interpreting that data into domain meaning is the Model's job.
- Dependency rule: `models/` and `workers/` may import from `infra/`; `infra/` imports nothing from `models/`, `views/`, or `controllers/`. Never `QtWidgets` — plain Python classes by default, `QtCore` (`QObject` + `Signal`) only when the client itself pushes events (e.g., data arriving on a socket).
- Blocking I/O calls (connect, read with timeout, requests) must be invoked from a worker (`references/threading.md`), never directly from a controller slot.
- For testability, controllers/models receive infra clients by injection like everything else — swapping a real `PLCClient` for a fake in tests is then trivial.

**Theme** (`theme/`)
- All app styling as code: `palette.py` holds color, spacing, and font constants; `styles.py` builds the QSS string from the palette (f-strings) and exposes `apply_theme(app)`.
- Called once in `main.py`, right after creating the `QApplication`: `apply_theme(app)`. Individual Views should not carry their own `setStyleSheet` calls except for punctual, widget-specific cases.
- Large static `.qss` files may live in `resources/` and be loaded by `styles.py` via `paths.resource_path()` — but the loading code stays in `theme/`, never scattered across Views.
- Views may import from `theme/` (e.g., a palette color for a chart); `theme/` imports from no other layer (utils allowed).

Minimal example:

```python
# src/theme/palette.py
PRIMARY = "#2563eb"
BACKGROUND = "#1e1e2e"
TEXT = "#e5e7eb"
FONT_FAMILY = "Segoe UI"
FONT_SIZE = 10
```

```python
# src/theme/styles.py
from PySide6.QtWidgets import QApplication

from src.theme import palette


def build_stylesheet() -> str:
    return f"""
        QWidget {{
            background-color: {palette.BACKGROUND};
            color: {palette.TEXT};
            font-family: "{palette.FONT_FAMILY}";
            font-size: {palette.FONT_SIZE}pt;
        }}
        QPushButton {{
            background-color: {palette.PRIMARY};
            border-radius: 4px;
            padding: 6px 12px;
        }}
    """


def apply_theme(app: QApplication) -> None:
    app.setStyleSheet(build_stylesheet())
```

**Utils** (`utils/`)
- Supporting code that belongs to no layer: pure functions and helpers reusable by Model, View, and Controller.
- What GOES here: shared constants (`constants.py`), validators (`validate_email`, `validate_date`), display formatters (`format_currency`, `format_date`), path resolution (useful for `resources/` and PyInstaller packaging), settings loading, logging setup.
- What does NOT go here: domain business rules (→ Model), reusable widgets or dialogs (→ `views/components/`), event orchestration (→ Controller).
- Prefer pure functions (input → output, no state) — they are trivial to test. Only create the utils files the project actually needs; don't generate all four empty files by default.
- Dependency rule: `utils` never imports from `models`, `views`, or `controllers` — only the other way around. This prevents import cycles. Formatting/path utils may import from `PySide6.QtCore` (e.g., `QStandardPaths`) if needed, but never from `QtWidgets`.

Rules for constants (`utils/constants.py`):
- Generic, app-wide constants go here: app name/version, window sizes, date formats, length limits. Any layer imports them via `from src.utils.constants import APP_NAME`.
- Domain constants do NOT go here — statuses, business limits, and closed value sets belong in the `models/` layer, preferably as an `Enum` (e.g., `src/models/order_status.py`). Same criterion as the rest of utils: if it knows the domain, it's Model.
- Constants are code; `resources/` holds only files (icons, images, qss). A constant may point to a resource via `paths.py` (e.g., `DEFAULT_ICON = resource_path("icons", "app.png")`), but never place `.py` files inside `resources/`.
- Constant ≠ setting: fixed values in code are constants; values the user can change (theme, last opened folder) belong to `config.py`, persisted in JSON/ini.

Example of `src/utils/constants.py`:

```python
APP_NAME = "My App"
APP_VERSION = "0.1.0"

WINDOW_MIN_WIDTH = 520
WINDOW_MIN_HEIGHT = 400

DATE_FORMAT = "dd/MM/yyyy"
MAX_NAME_LENGTH = 100
```

Example of `src/utils/paths.py`, useful in any project with `resources/` (two levels above `src/utils/paths.py` is `src/`, where `resources/` lives):

```python
import sys
from pathlib import Path


def src_root() -> Path:
    """The src/ directory, compatible with normal execution and PyInstaller."""
    if getattr(sys, "frozen", False):
        return Path(sys._MEIPASS)  # bundled executable
    return Path(__file__).resolve().parent.parent  # src/


def resource_path(*parts: str) -> Path:
    """E.g.: resource_path('icons', 'save.png')"""
    return src_root() / "resources" / Path(*parts)
```

**`main.py`** (at the project root)
```python
import sys
from PySide6.QtWidgets import QApplication

from src.models.user_model import UserModel
from src.views.main_view import MainView
from src.controllers.main_controller import MainController


def main():
    app = QApplication(sys.argv)
    model = UserModel()
    view = MainView()
    controller = MainController(model=model, view=view)
    view.show()
    sys.exit(app.exec())


if __name__ == "__main__":
    main()
```

Run with `uv run main.py` (from the project root).

Keep a live reference to the controller (as above — a local variable in `main()` is enough). If the controller gets garbage-collected, the signal connections die silently.

## Dependency management with uv (do NOT use pip)

This project uses **uv** as the package and environment manager. NEVER suggest `pip install`, `python -m venv`, or `requirements.txt` — the uv equivalent is always:

```bash
# Create a new project (generates pyproject.toml, .python-version, and main.py at the root; then create src/ and the MVC folders)
uv init my_project
cd my_project

# Add dependencies (updates pyproject.toml and uv.lock)
uv add pyside6

# Run the application (resolves the environment automatically)
uv run main.py

# Development dependencies (tests, lint)
uv add --dev pytest pytest-qt ruff

# Sync the environment after cloning the repository
uv sync
```

Rules:
- It is a UI application, not a distributable package: do NOT add `[project.scripts]` or `[build-system]` to `pyproject.toml`, and do not use `uv init --package`.
- The default `uv init` already creates `main.py` at the root — keep it there and just replace its content with the MVC entry point.
- Run instructions for the user always use `uv run main.py` (not `python main.py`).
- Dependencies go into `pyproject.toml` via `uv add` — don't hand-edit the `dependencies` section without need, and never create `requirements.txt`.
- For a new project, generate a minimal uv-compatible `pyproject.toml` if you cannot run commands:

```toml
[project]
name = "my-project"
version = "0.1.0"
description = "PySide6 desktop application in MVC"
requires-python = ">=3.10"
dependencies = [
    "pyside6>=6.6",
]
```

## Code conventions

- Qt imports always grouped: `from PySide6.QtWidgets import ...`, `from PySide6.QtCore import Qt, Signal, Slot`.
- Custom signals declared as class attributes: `data_changed = Signal(list)`.
- Use `@Slot()` on controller methods connected to signals (documentation and a small performance gain).
- Names in English or the user's language, matching the user's existing code; in a new project, follow the language the user writes in during the conversation.
- Widgets the controller needs to access are public attributes of the View; purely structural widgets (layouts, static labels) may stay local.
- For lists/tables with lots of data, prefer Qt's native models (`QAbstractTableModel`, `QAbstractListModel`) inside the `models/` folder — they fit well with the project's MVC (they are the "M" from Qt's point of view) and avoid repopulating tables by hand.

## Workflow when handling requests

1. **New project**: create the full structure (`main.py` at the root + MVC folders with `__init__.py` inside `src/`), a minimal working example for the requested domain, and the uv `pyproject.toml`. The app must run with `uv run main.py` without edits (after `uv sync`/`uv add pyside6`).
2. **New screen/feature in an existing project**: read the existing files first to follow the conventions already in use; create the Model/View/Controller trio (or reuse existing layers) and register the integration in the main controller.
3. **Refactoring monolithic code**: identify what is data/rules (→ Model), what is widget/layout (→ View), and what is wiring/orchestration (→ Controller). Preserve the original behavior; refactor in verifiable steps.
4. When done, briefly explain the flow of one event (e.g., "Save click → `MainController.save()` → `UserModel.add()` → `data_changed` signal → `MainView.update_table()`").

## Reference files

Read the relevant reference in `references/` BEFORE generating code when the request matches:

- `complete-example.md` — working reference example (a user CRUD with a Model emitting signals, a View with form + table, and a Controller wiring everything). Read it the first time you use this skill or when the request involves tables/lists.
- `threading.md` — REQUIRED reading whenever the request involves database access, HTTP/API calls, file processing, hardware/test execution, or anything that could block the UI. The project's single threading standard is `QThread` (subclass + `run()`): generic, self-contained workers that receive plain data in `__init__` and declare their own signals; the reference contains the one-shot, generic-callable, and continuous/cancellable templates.
- `multi-window.md` — REQUIRED reading whenever the app has more than one screen: dialogs, extra windows, wizards, settings screens. Covers dialogs opened by controllers, sharing one Model instance across screens, and controller-to-controller communication.

## Common pitfalls to avoid

- View importing the Model, or Model importing anything from `PySide6.QtWidgets` — breaks the separation.
- Business logic inside click handlers in the View.
- Connecting signals inside the View to itself when the action involves data — that's the controller's job.
- Forgetting `sys.exit(app.exec())` or instantiating more than one `QApplication`.
- Turning `utils/` into a dumping ground: if the function knows the domain (user, order, product...), it belongs to the Model, not utils.
- Blocking the UI with long-running operations in the controller — use the `QThread` worker pattern from `references/threading.md` and communicate results via signals.
- Creating a second instance of a Model for a second screen — screens drift apart silently. Share the instance (see `references/multi-window.md`).
- Calling blocking infra I/O (PLC read, serial, HTTP) directly in a controller slot — wrap it in a worker.
- Scattering `setStyleSheet` calls across Views — styling is centralized in `theme/` and applied once in `main.py`.
